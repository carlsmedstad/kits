## r2-F1 | kits/kit-arch-development/files/arch-rdepends:189 | must-fix

Claim: `--repo` also restricts where the *targets* are looked up, so a query
whose target package lives outside the named repositories silently loses every
match that went through `%PROVIDES%` — brief requirement 2 ("querying `bash`
finds packages that depend on `sh`") is unconditional, but `--repo` turns it off.

Because: `dbs` (lines 188-207) selects which `.db` files are unpacked into
`$tmp/desc` (lines 228-232), and that one file is fed to the awk program three
times: pass 2 harvests the provides of the targets, pass 3 matches dependents.
Restricting `dbs` therefore restricts both. `bash` is in `core`, so under
`--repo extra` its `%PROVIDES% sh` is never read:

    T=kits/kit-arch-development/files/arch-rdepends
    $T --repo extra --columns pkgname bash | wc -l                     # 575
    $T --columns pkgname,repository bash | awk -F'\t' '$2=="extra"' | wc -l  # 772

197 `extra` packages that depend on `sh` are dropped, with no diagnostic. The
same happens for sonames: `--repo extra icu` returns 218 rows against 220 for
the unrestricted run, missing the packages that depend on `libicuuc.so`. The
fix is to harvest provides from every synced database and apply the `--repo`
filter only to the rows that are printed.

Verified: by running the two commands above on /var/lib/pacman/sync.

## r2-F2 | kits/kit-arch-development/files/arch-rdepends:265 | must-fix

Claim: when two or more queried packages provide the same name, `want` keeps
only the last provider seen in the database stream, so the `target` column
misattributes every row matched through that shared provide, and a queried
package can vanish from the `target` column entirely.

Because: `want` is a name -> single-target map. Pass 2 records
`provides[bare($0)] = pkgname` (line 273), overwriting on collision, and line
265 merges one value per name into `want`. `jack2` and `pipewire-jack` both
provide `jack`:

    T=kits/kit-arch-development/files/arch-rdepends
    $T --columns pkgname jack2         | wc -l   # 527
    $T --columns pkgname pipewire-jack | wc -l   # 476
    $T --columns pkgname,target jack2 pipewire-jack | cut -f2 | sort | uniq -c
    #   60 jack2
    #  476 pipewire-jack

Queried alone, `jack2` has 527 reverse dependencies; queried alongside
`pipewire-jack`, only 60 rows are labelled `jack2` — 467 rows claim the wrong
target. Worse, a target can disappear: `exim`, `opensmtpd` and `postfix` all
provide `smtp-server`, and

    $T --columns target exim opensmtpd postfix   # prints only: exim, postfix
    $T --columns target opensmtpd                # prints: opensmtpd

`opensmtpd` is silently absent. Brief requirement 6 defines `target` as "the
queried package the row was matched against, resolved through provides", and
requirement 7 puts one row per printed-column tuple, so a package depending on
`smtp-server` should yield a row per matching target. `want` needs to hold a
set of targets per name, and the match rule needs to emit one row per member.

Verified: by running the commands above on /var/lib/pacman/sync.

## r2-F3 | kits/kit-arch-development/files/arch-rdepends:298 | should-fix

Claim: the type-joining awk miscounts the output columns when `--columns` names
exactly one non-`type` column and that column's value is the empty string; it
prints a truncated row (an empty line) instead of the row.

Because: `emit()` reconstructs the row as `n + 1` fields where
`n = split(key, fields, "\t")`, but awk's `split("")` returns 0, not 1, so a
single empty key field is counted as zero fields and one column is lost. The
only column whose value can be empty is `version`/`upstream`, which comes
through `jq`'s `.local_version // "-"` — that guard turns `null` into `-` but
leaves `""` alone. With a result file carrying an empty `local_version`:

    printf '[{"pkgbase":"libssh","local_version":"","upstream_version":"0.11.2","out_of_date":true}]' > /tmp/nv.json
    kits/kit-arch-development/files/arch-rdepends \
      --nvcheck /tmp/nv.json --repo extra --columns version,type -o cmocka | cat -A
    # prints "$" (an empty line); expected "^Imakedepend$"

`--columns version,pkgbase,type` on the same file prints the row correctly, which
confirms the fault is the single-empty-key case. Filed should-fix rather than
must-fix only because `arch-nvcheck` itself never writes an empty
`local_version` (it writes `null` on failure, line 224 of `arch-nvcheck`), so
the trigger needs a hand-written or third-party `--nvcheck` file — which the
option explicitly invites. Either widen the `jq` guard to
`(.local_version // "" | if . == "" then "-" else . end)` or count the key
fields from `keycols` instead of from `split()`.

Verified: by running the two commands above.

## r2-F4 | kits/kit-arch-development/files/arch-rdepends:287 | should-fix

Claim: the two-stage type join rests on an unstated invariant — that
`LC_ALL=C sort -u` leaves all rows sharing a key adjacent, which holds only
because TAB (0x09) collates below every byte a key value can contain. Nothing
in the diff records or checks it, and dropping or weakening `LC_ALL=C` silently
splits a group into duplicate rows rather than failing.

Because: the first awk emits `<key fields>\t<rank digit>`; the second awk
(lines 296-319) groups *consecutive* lines by `$1..$(NF-1)`. Under a collation
that ignores punctuation, a longer key can sort between two rows of a shorter
key:

    printf 'ab\t0\nab\t3\nab1\t0\n' > /tmp/raw.txt
    LC_ALL=C           sort -u /tmp/raw.txt   # ab/0, ab/3, ab1/0  -> ab depend,checkdepend
    LC_ALL=en_US.UTF-8 sort -u /tmp/raw.txt   # ab/0, ab1/0, ab/3  -> ab depend / ab1 depend / ab checkdepend

I re-ran the whole tool with `LC_ALL=en_US.UTF-8` substituted on line 287
against `glibc`, `bash`, `gcc-libs`, `python` and `cmake` and got identical
output, so the current code is correct — this is a latent invariant, not a live
bug. The repository has no test harness at all (no CI workflow, no `check`
target in `Makefile`), so nothing pins it. CLAUDE.md's comment policy names
exactly this case as a comment worth keeping ("a non-obvious invariant needed
to prevent a plausible regression"); one line above the `sort` saying that the
grouping needs byte order because TAB must sort below the key bytes would
discharge it.

Verified: by running the `printf`/`sort` pair above through a copy of the
script's grouping awk, and by running a `LC_ALL=en_US.UTF-8` copy of the whole
script (in the scratchpad, not the tree) against five queries.

## r2-F5 | kits/kit-arch-development/files/arch-rdepends:138 | note

Claim: a trailing comma is silently accepted in `--columns`, `--deptype` and
`--repo`, and an empty `--deptype` or `--repo` silently means "all", while an
empty `--columns` is an error.

Because: `IFS=, read -ra requested <<< "$columns"` drops the empty field a
trailing comma produces, so `--columns pkgname,` succeeds and prints one column;
`--columns ,pkgname` and `--columns pkgname,,repository` correctly error with
`: invalid column`, which shows the inconsistency is accidental. Likewise
`deptypes=` and `repos=` are tested with `[ -n ... ]` (lines 168, 189), so
`--deptype ''` searches all four types and `--repo ''` searches all databases,
whereas `--columns ''` exits 1 per brief requirement 10. Brief requirement 6
says unknown names are errors; the empty name is arguably one. Cosmetic — no
wrong output results.

    kits/kit-arch-development/files/arch-rdepends --columns pkgname, cmocka  # rc=0
    kits/kit-arch-development/files/arch-rdepends --columns ,pkgname cmocka  # rc=1

Verified: by running both commands.

## What I could not check

- I could not exercise a repository set larger than this machine's synced
  databases (`core`, `core-testing`, `extra`, `extra-testing`, `kits`); in
  particular `multilib` is not enabled here, so `lib32-*` provides collisions
  were not covered. F2's mechanism is repository-independent.
- I could not test against a database written by an older `repo-add` that
  splits `%MAKEDEPENDS%` into a separate `depends` member; every entry in the
  five local databases carries a single `desc` member (`bsdtar -tf` shows only
  `*/desc`), and all 15514 entries carry a `%BASE%` section after their
  `%NAME%`, so the `--include='*/desc'` restriction and the pkgbase fallback are
  safe here but unverified for archived or third-party repositories.
- The tty branch of `format` was exercised through `script -qec`, not a real
  terminal; alignment and the header row rendered correctly there.

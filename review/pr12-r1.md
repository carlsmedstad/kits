## r1-F1 | kits/kit-arch-development/files/arch-rdepends:273 | must-fix

Claim: Treating a provided name as belonging to exactly one queried target loses valid target relationships whenever two queried packages provide the same name.

Because: Consider `provider-a` and `provider-b`, both providing `virtual-api`, and `consumer`, which depends on `virtual-api`. Each provider queried individually has `consumer` as a reverse dependency. The combined query must retain both relationships when the target column is shown:

```sh
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --columns pkgname,target provider-a
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --columns pkgname,target provider-b
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --columns pkgname,target provider-a provider-b
```

The scalar `provides[name]`/`want[name]` model retains only the last provider encountered. Adding a query target can therefore erase a previously reported relationship, and archive order decides which target survives. This is a cardinality error in the proposed lookup model: provides is a relation, not a unique owner map. No version-constraint comparison or provider-installation choice is needed for this counterexample. Preserve `(provided-name, queried-target)` membership and emit every matching relationship; final output deduplication can collapse them when `target` is omitted.

Verified: by reasoning — two distinct target relationships cannot be recovered from a single stored target, regardless of parsing correctness.

## r1-F2 | kits/kit-arch-development/files/arch-rdepends:281 | must-fix

Claim: Using the selected display columns as the dependency-type grouping key can report a combination of types that no matching package actually uses.

Because: Consider `consumer-a` with only a runtime dependency on `libfoo`, and `consumer-b` with only a make dependency on `libfoo`. Compare:

```sh
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --columns pkgname,type libfoo
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --columns type libfoo
```

The first query distinguishes `consumer-a / depend` and `consumer-b / makedepend`. With only `type` selected, package identity is discarded before grouping, leaving one empty grouping key; the result becomes `depend,makedepend`. Neither package has that combination. The same loss occurs when distinct split packages share a displayed pkgbase, or unrelated packages share another selected value. A presentation choice consequently changes the underlying facts rather than merely hiding columns. Aggregation and projection do not commute here: first collect types for each package/repository/target relationship, then select columns and deduplicate complete displayed rows. With that order, the type-only example yields separate `depend` and `makedepend` rows.

Verified: by reasoning — grouping after removal of entity identity merges distinct relationships; later formatting cannot reconstruct their original type sets.

## r1-F3 | kits/kit-arch-development/files/arch-rdepends:188 | should-fix

Claim: Sharing one repository scope between target resolution and consumer search silently omits consumers when a queried package's provides metadata resides outside the requested result repositories.

Because: Consider a synced `core.db` containing `libfoo`, which provides `libfoo.so`, and a synced `extra.db` containing `consumer`, which depends on `libfoo.so`. These commands should differ only in which consumers are eligible for display:

```sh
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --columns pkgname libfoo
kits/kit-arch-development/files/arch-rdepends --dbpath "$dbroot" --repo extra --columns pkgname libfoo
```

The unrestricted lookup can discover the relationship. Restricting the databases before resolving `libfoo` removes the metadata needed to discover the same consumer, even though `consumer` remains inside the requested repository and all necessary metadata is locally available. Direct dependencies on `libfoo` still match, so the filtered result can look plausible while being incomplete. This weakens the useful operation “show this library's consumers in extra/multilib.” Separate the scopes: resolve queried targets using all synced databases, then restrict dependent rows to the requested repositories. This remains entirely local and does not require fetching databases or adding transitive traversal.

Verified: by reasoning — an output filter applied to the lookup's reference data removes the only mapping from `libfoo` to `libfoo.so`, so the restricted search cannot recognize that edge.

## r2-F1 | kits/kit-arch-development/files/arch-nvtodo:80 | must-fix

Claim: A `provides` entry silently overwrites the `pkgname` -> pkgbase mapping of
a real package of the same name, so `arch-nvtodo` orders a todo package after a
package it does not depend on and *not* after the one it does; which of the two
wins depends only on glob order, so it is locale-dependent.

Because: lines 79 and 80 both write into the same `owner[]` array with last-write
-wins, and files are visited in glob (locale collation) order. This is live in
the user's cache today: running the diff's own extractor over
`/home/carsme/.cache/arch-nvcheck/*/.SRCINFO` yields `owner["aws-cli"] =
aws-cli-v2`, because `aws-cli-v2/.SRCINFO` sorts after `aws-cli/.SRCINFO` and
carries `provides = aws-cli`. (`python-h5py` is a second live collision that only
resolves correctly by glob luck: `python-h5py-openmpi/.SRCINFO` happens to sort
*before* `python-h5py/.SRCINFO` under en_US.UTF-8; under `LC_ALL=C` the
`python-h5py` <- `python-xarray`, `python-h5netcdf` and `python-spyder-kernels`
edges would all be misattributed to `python-h5py-openmpi`.)

Minimal reproduction with the same .SRCINFO shapes:

```sh
D=$(mktemp -d); mkdir -p $D/arch-nvcheck/{aws-cli,aws-cli-v2,consumer}
printf 'pkgbase = aws-cli\n\npkgname = aws-cli\n' > $D/arch-nvcheck/aws-cli/.SRCINFO
printf 'pkgbase = aws-cli-v2\n\tprovides = aws-cli\n\npkgname = aws-cli-v2\n' > $D/arch-nvcheck/aws-cli-v2/.SRCINFO
printf 'pkgbase = consumer\n\tdepends = aws-cli\n\npkgname = consumer\n' > $D/arch-nvcheck/consumer/.SRCINFO
printf '%s\n' aws-cli aws-cli-v2 consumer \
  | jq -R -s 'split("\n")|map(select(.!=""))|map({pkgbase:.,status:"success",out_of_date:true})' > $D/t.json
XDG_CACHE_HOME=$D bash kits/kit-arch-development/files/arch-nvtodo $D/t.json
```

Output:

```
Batch 1
 aws-cli
 aws-cli-v2

Batch 2
 consumer (after: aws-cli-v2)
```

`consumer` depends on `aws-cli`, yet the todo list never orders it after
`aws-cli` and instead orders it after an unrelated package. A real pkgname must
win over a `provides` of the same name.

Verified: by running — the two commands above, plus the diff's awk program run
over `/home/carsme/.cache/arch-nvcheck/*/.SRCINFO` with an `END` block printing
`owner["aws-cli"]`.

## r2-F3 | kits/kit-arch-development/files/arch-nvtodo:97 | must-fix

Claim: `walk()` annotates an edge `(via X)` even when the dependent package
depends on the todo package *directly*, whenever some other, alphabetically
earlier, non-todo dependency also reaches it. The `after:` annotation then states
a relationship that does not exist.

Because: `walk` is a DFS over `pred[node]` in edges-file (alphabetical) order and
`visited[d, target]` is set on first arrival, so the first path found wins rather
than the direct edge. Live-data case, from the real cache:

```sh
printf '%s\n' aws-c-io aws-sdk-cpp \
  | jq -R -s 'split("\n")|map(select(.!=""))|map({pkgbase:.,status:"success",out_of_date:true})' > /tmp/aws.json
bash kits/kit-arch-development/files/arch-nvtodo /tmp/aws.json
```

```
Batch 2
 aws-sdk-cpp (after: aws-c-io (via aws-c-auth))
```

`/home/carsme/.cache/arch-nvcheck/aws-sdk-cpp/.SRCINFO` line 12
(`makedepends = aws-c-io`) and line 80 (`depends = aws-c-io`) make this a direct
dependency; `aws-c-auth` sorts before `aws-c-io`, so the indirect path is walked
first. On a realistic 200-package todo set drawn from the live cache, 12 of the
159 `(via ...)` annotations are spurious in this way (gammu/libdbi,
libusbmuxd/libplist, hid-tools/python-click, libimobiledevice/libplist,
python-awscrt/aws-c-cal, python-awscrt/aws-c-io, gnuradio-osmosdr/libuhd,
gnuradio-osmosdr/libvolk, gqrx/libvolk, python-aws-sam-translator/python-botocore,
syslog-ng/python-botocore, syslog-ng/python-urllib3). The brief's step 2 says the
via records "the first intermediate package" on a path that goes *through*
packages not on the list; a direct dependency has no intermediate. Visiting the
direct predecessors of the target before recursing (or a BFS) fixes it.

Verified: by running — the two commands above, plus a validator that cross-checks
every emitted `(via V)` against the direct-edge set produced by the diff's own
`.SRCINFO` extractor.

## r2-F4 | kits/kit-arch-development/files/arch-nvcheck:158 | should-fix

Claim: A single failing `pkgctl repo clone` or `git pull` aborts the whole run
with exit 123 and leaves the result file untouched, so no fresh result is ever
recorded — which defeats the incremental progress `--max-age` and the result file
exist to provide.

Because: both `xargs` calls run under `set -e` and `xargs` exits 123 if any child
exits 1-125. With 582 clones over the network, one transient failure discards
every result the run would have produced, and the next `--max-age` run repeats the
whole check. Reproduced with stub `git`/`pkgctl` on PATH:

```sh
# git stub that fails for one pkgbase, pkgctl stub that succeeds
bash kits/kit-arch-development/files/arch-nvcheck -m me   # -> exit=123, check-me.json unchanged
# pkgctl stub whose `repo clone` fails for one pkgbase
bash kits/kit-arch-development/files/arch-nvcheck -m me   # -> exit=123, check-me.json unchanged
```

Both `xargs` invocations should tolerate per-package failure (report the pkgbase
on stderr and carry on), so the run still writes what it managed to check.

Verified: by running — stub `arch-ls`, `pkgctl` and `git` on `PATH` with
`XDG_CACHE_HOME` pointed at a scratch cache; both cases printed `exit=123` and
`diff -q` reported the result file byte-identical to the pre-run copy.

## r2-F5 | kits/kit-arch-development/files/arch-nvcheck:172 | should-fix

Claim: If `xargs` splits the `pkgctl version check` command line into more than
one invocation, `jq` emits one array per invocation and `--slurpfile new` +
`$new[0]` keeps only the first, silently dropping every package checked after the
first chunk. This is an invariant the diff introduces (`new.json` holds exactly
one JSON array) that nothing enforces or tests.

Because: `xargs` on this machine caps the command buffer at 131072 bytes
(`xargs --show-limits`), which splits at roughly 20000 pkgbases; the 582 clones in
the live cache take 7374 bytes, so it does not fire today. The failure is silent
when it does — no error, just a shorter result file, and under a full run `keep`
is empty so the dropped entries are not recovered from the old file either. The
mechanism:

```sh
printf '[{"pkgbase":"a"}]\n[{"pkgbase":"b"}]\n' > /tmp/split.json
: > /tmp/keep0; echo '[]' > /tmp/old0
jq -n --rawfile keep /tmp/keep0 --slurpfile old /tmp/old0 --slurpfile new /tmp/split.json \
  '($keep|split("\n")|map(select(.!="")|{(.):true})|add // {}) as $keep
   | ($old[0]|map(select($keep[.pkgbase]))) + $new[0] | sort_by(.pkgbase)'
# -> [{"pkgbase":"a"}]   ("b" is gone)
seq 1 20000 | sed 's/^/pkg/' | xargs echo INVOCATION | grep -c INVOCATION   # -> 2
```

Using `jq -s 'add'` over `new.json` (or `xargs -n` with an explicit accumulate)
removes the invariant.

Verified: by running — the two commands above.

## r2-N1 | kits/kit-arch-development/files/arch-nvtodo:138 | note

Claim: `asort()` is a gawk extension and sorts in byte order, so the within-batch
listing is not in the locale collation order the rest of the pipeline (`sort -u`,

Because: `gawk` is in `base` on Arch so the portability half is theoretical, but

and fails `sort -c` under the ambient `en_US.UTF-8` (first disorder at

the two agree and drop the gawk dependency.

Verified: by running — `sort -c` and `LC_ALL=C sort -c` over the batch-1 member
list extracted from a full-cache run of `arch-nvtodo`.

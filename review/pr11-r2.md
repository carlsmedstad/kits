## r2-F1 | kits/kit-arch-development/files/arch-nvcheck:228 | must-fix

Claim: a positional pkgbase containing `/` — most plausibly a tab-completed
`hiredis/` typed in the cache directory, or a pasted `extra/hiredis` — makes the
run abort and truncates `check-<maintainer>.json` to 0 bytes, destroying the
whole result file including entries the same run had already checked.

Because: `worker()` builds `entry=$tmp/entries/$1` from the argument verbatim,
so `check_one "$pkg" > "$entry.tmp"` redirects into a directory that does not
exist. The redirection fails, `check_one` never runs, `mv` fails, but `worker`'s
last command is `echo "$pkg"`, so it still reports the package as finished and
exits 0. The main loop then calls `merge "$tmp/entries/aa/"`, whose
`jq --slurpfile entry` cannot open the path and exits non-zero — and
`write_result` (line 194) installs its empty output over the result file anyway.
Nothing validates the positional arguments; `$#`-mode input goes straight from
`printf '%s\n' "$@"` (line 171) to `xargs` (line 266) to this path.

Reproduce, no stubs needed (`pkgctl` is never reached):

    d=$(mktemp -d); mkdir -p "$d/arch-nvcheck"
    echo '[{"pkgbase":"aa","status":"success","message":null,"local_version":"1","upstream_version":"1","out_of_date":false,"checked_at":"2026-01-01T00:00:00Z"}]' \
      > "$d/arch-nvcheck/check-me.json"
    XDG_CACHE_HOME=$d bash kits/kit-arch-development/files/arch-nvcheck -m me 'aa/'
    stat -c%s "$d/arch-nvcheck/check-me.json"   # 0

With a stubbed `pkgctl` and the arguments `aa/ bb cc dd ee`, `cc bb dd ee` were
all checked successfully and their entries were still lost: exit 2, result file
0 bytes. That contradicts R11 ("A run interrupted at any point keeps every
finished entry") and the brief's "The run no longer aborts on a per-package
failure".

Verified: by running (the commands above, plus the stubbed five-package variant).

## r2-F2 | kits/kit-arch-development/files/arch-nvcheck:194 | must-fix

Claim: `write_result` renames its temp file over the result file even when the
`jq` that feeds it failed and produced nothing, so any producer error replaces
the maintainer's result file with an empty file instead of leaving it intact.

Because:

    write_result() {
      cat > "$tmp/result.json"
      mv -f "$tmp/result.json" "$result_file"
    }

`cat` succeeds on an empty stream, so `mv` runs unconditionally. `set -o
pipefail` then aborts the run — after the damage. Both writers are exposed:
`merge` (line 234, called once per finished package inside the main loop) and
the retain-prune at line 199. R11 asks for "the atomic rename"; the rename here
is atomic but not conditional on success, which is the half that protects the
file. The guard needs to be on the exit status of the producer, e.g. capture
`jq`'s status and skip the `mv` (and keep going) when it is non-zero, rather
than `cat`-then-`mv`. Note also that a `merge` failure currently kills the
whole run via `set -e` in the pipeline subshell, which is the second half of
the R11 contradiction in r2-F1.

Verified: by running — the r2-F1 repro is the observed instance; the code path
is the two `| write_result` call sites at lines 202 and 237.

## r2-F3 | kits/kit-arch-development/files/arch-nvcheck:185 | must-fix

Claim: once `check-<maintainer>.json` is zero bytes, every later `arch-nvcheck`
run becomes a silent no-op — it checks nothing, writes nothing, prints nothing
and exits 0, so the user reads "no out-of-date packages" from a tool that never
looked.

Because: `jq` on a zero-byte input has no inputs, so it runs the program zero
times, emits nothing and exits 0. `$tmp/old.json` is a byte copy of the result
file (line 159), so line 185's `jq ... > "$tmp/check"` yields an empty work
list, `total` is 0, `xargs --no-run-if-empty` runs nothing, the prune at line
199 writes another empty file, and `render` (line 130) prints nothing. The
`--cached` guard at line 138 only tests `-f`, so `--cached` is silent too.
Nothing on stdout or stderr distinguishes this from "everything is up to date".
This is reachable on its own (a truncated file from any cause) as well as from
r2-F1/r2-F2. Loading the old file should reject a non-array or empty document
loudly, or fall back to `[]` with a warning.

Reproduce:

    d=$(mktemp -d); mkdir -p "$d/arch-nvcheck"; : > "$d/arch-nvcheck/check-me.json"
    XDG_CACHE_HOME=$d bash kits/kit-arch-development/files/arch-nvcheck -m me --cached; echo $?
    # prints nothing, exits 0

With a stubbed `arch-ls`/`pkgctl` a full run over five packages against a
zero-byte file checked zero packages (the stub's invocation log stayed empty)
and exited 0.

Verified: by running.

## r2-F4 | kits/kit-arch-development/files/arch-nvcheck:194 | should-fix

Claim: the result-file merge invariant that this diff introduces — "the main
loop merges each finished entry at once and the file is never left in a worse
state than before the run" (R11) — has no fixture, harness or self-check in the
tree, and it is exactly where r2-F1 through r2-F3 live.

Because: commits e910fc8, 8d64ea0 and 4dd78d6 move the single end-of-run write
into a per-package merge loop driven by `xargs -P`, `worker` temp files and
`write_result`. Nothing in the repository exercises it; the brief's "Out of
scope for now" section and R8 keep automated tests out, and the earlier round
verified these invariants by hand only. I am reporting the tension rather than
resolving it: my lens files an uncovered new invariant at should-fix or above,
and R8 says tests stay out. The minimum that does not need a harness is to make
the invariant self-enforcing in the script — guard the rename on the producer's
status (r2-F2) and reject an unusable old file (r2-F3) — so the property holds
by construction instead of by inspection. If a harness is wanted, the stub
`arch-ls`/`pkgctl`/`git` shape used in both review rounds is enough to cover
merge, ordering, freshness and interruption in a few dozen lines.

Verified: by reasoning (over the diff and the brief's out-of-scope list); the
three defects above are the running evidence that the area is uncovered.

## r2-F5 | kits/kit-arch-development/files/arch-nvcheck:166 | note

Claim: if `arch-ls` succeeds but returns an empty list — an archweb search that
answers 200 with `"results": []` for a still-valid maintainer — the full run
prunes the result file to `[]` and the maintainer's whole history is gone.

Because: `sort -u pkgs.txt > candidates; cp candidates retain` (lines 168-169)
followed by the prune at line 199 leaves `map(select($retain[.pkgbase]))` with
an empty retain set. `arch-ls` runs with `set -euo pipefail` and
`curl --fail-with-body`, so a transport or HTTP failure does abort
`arch-nvcheck` before the prune — this only bites when the API answers
successfully with nothing. The spec's overwrite rule ("Packages no longer
maintained drop out") sanctions `[]` for a maintainer who really has no
packages, which is why this is a note and not a defect; the recovery is also
benign, since `[]` is valid JSON and the next good run repopulates it. A
"refusing to empty the result file, arch-ls listed no packages" guard would
still be cheap.

Verified: by reasoning (lines 164-174 and 199-202; not run, since it needs a
lying archweb).

## r2-F6 | kits/kit-arch-development/files/arch-nvtodo:196 | note

Claim: a cycle member that tsort happens to place in the earliest batch shows
no dependencies at all in the default listing, so the line gives no hint that
its order was the arbitrary one.

Because: the default annotation is `else if (batch[d] == b - 1)`. For a cycle
broken with `a` in batch 1 and its dependency `b` in batch 3, `batch[b]` is 3,
never `0`, so `a`'s line prints bare. The stderr warning does name the cycle,
and `--deps` shows the edge, so nothing is lost — but the two outputs disagree
about `a`. Observed on a 3-cycle fixture:

    arch-nvtodo: warning: a, c and b depend on each other, their order is arbitrary
    Batch 1
     a 1.0 -> 2.0
    ...
    Batch 3
     b 1.0 -> 2.0  (c)

The brief only requires "reported on stderr and broken arbitrarily; no package
is dropped", both of which hold, so this is out-of-scope polish.

Verified: by running (a 3-cycle `.SRCINFO` fixture under a scratch
`XDG_CACHE_HOME`).

## r2-F7 | kits/kit-arch-development/files/arch-nvtodo:143 | note

Claim: `arch-nvtodo` needs gawk specifically — `gensub()` at line 143 and
`asort()` at line 188 are gawk extensions — and `gawk` is not in the kit's
`depends`.

Because: `kits/kit-arch-development/PKGBUILD.in` lists `jq` explicitly but no
awk. In practice `gawk` arrives with the `base` metapackage on every Arch
install, so this never fails in the field; it is a declaration gap, not a bug.
`tsort` (coreutils) and `getopt` (util-linux) are undeclared for the same
reason.

Verified: by reasoning (grep of the two gawk builtins against the PKGBUILD's
`depends` array).
